# OryxOS 与 Hermes Agent 的技术思考

我把 Hermes Agent 的功能概览和 oryxos 的代码、README、CLAUDE.md 及模块划分放在一起看，得到的核心判断是：

> **Agent 不是“接了大模型的聊天机器人”，而是一个能在上下文中持续决策、调用外部能力、观察结果、修正计划并交付结果的运行实体。**  
> 大模型负责生成判断，Agent 还必须具备工具、执行循环、上下文、记忆、权限边界、交互入口和结果交付机制。

Hermes 文档也明确把工具、技能、持久化记忆、上下文文件、定时任务、子 Agent、代码执行、事件钩子、浏览器、语音、MCP、提供者路由等组合起来，定位为“自主助手”而非基础聊天能力。[Hermes Agent 功能概览](https://hermesagent.org.cn/docs/user-guide/features/overview)

## 一、两者是什么

| 维度 | Hermes Agent | oryxos |
|---|---|---|
| 产品形态 | 面向个人开发者和技术用户的自主助手 | 面向企业部署的 Agent 运行平台 / Agent OS |
| 核心对象 | 一个能够操作本地环境、网络和消息平台的 Agent | 多个可管理、可审计、可调度的企业 Agent |
| 主要入口 | CLI、消息平台、API、IDE 集成 | REST API、Web 管理台、CLI、多种消息渠道 |
| 使用方式 | 直接与 Agent 对话，也可以让它执行任务 | 定义 Agent，再通过 API、渠道或调度任务调用 |
| 典型问题 | “帮我完成这个开发、研究或自动化任务” | “如何让企业持续运行一批受治理的 Agent” |

两者都承认几个基本事实：模型本身不能直接完成复杂工作；工具调用需要执行环境；长期任务需要记忆；复杂工作需要拆分或委派；安全性不能只依赖提示词。

## 二、功能层面的区别

### 1. Hermes 更强调“个人助手的任务覆盖面”

Hermes 的功能面比较宽，尤其覆盖个人工作环境：

- 终端执行、文件编辑、网络搜索、记忆管理；
- 自动发现 `.hermes.md`、`AGENTS.md`、`CLAUDE.md`、`SOUL.md` 等上下文文件；
- 使用 `@` 引用文件、目录、Git diff 和 URL；
- 修改文件前创建检查点，并通过 `/rollback` 回滚；
- 浏览器自动化，支持本地 Chrome、Chromium 和云端浏览器；
- 语音模式、TTS、语音转录、图像粘贴、图像生成；
- 通过 `delegate_task` 启动最多 3 个并行子 Agent；
- 通过 `execute_code` 将多步工具调用压缩到一次模型调用；
- 批量运行大量提示，生成 ShareGPT 轨迹数据；
- MCP、OpenAI 兼容 API、ACP/IDE 集成；
- 多提供者路由、备用提供者、凭证池和外部记忆后端。

这使 Hermes 更像一个“能力很丰富的个人自动化工作台”。它的重点是让一个用户能够把开发、研究、浏览器操作、语音交互和消息协作放到同一个 Agent 中。

### 2. oryxos 更强调“企业 Agent 的标准化运行”

oryxos 当前已经实现或明确设计的重点包括：

- 一个目录对应一个 Agent：`AGENT.md` 描述身份、任务和运行配置；
- 自实现 ReAct Loop，模型只负责决策，ToolExecutor 负责实际执行；
- 动态 Provider Registry，可运行时增删模型提供者；
- 内置文件、Shell、HTTP 工具，以及 MCP 扩展；
- Skills、Memory、Knowledge 的模块化组合；
- 每个 Agent 独立的长期记忆；
- 知识库的分块、向量检索、关键词检索和 RRF 融合；
- 文件路径、命令、域名白名单；
- `tool_invocations` 和 `llm_calls` 审计表；
- Cron 调度、通知渠道、REST API 和 Web 管理台；
- 多个 Agent 在同一个实例中共存；
- WorkspaceWatcher 监听目录变化，Agent 可热加载。

因此，oryxos 的差异不在于“能不能调用更多工具”，而在于是否把 Agent 变成一种可以被企业部署、配置、审计、治理和持续运行的基础设施对象。

### 3. 功能重叠与明显差异

| 能力 | Hermes | oryxos |
|---|---|---|
| 工具调用 | 工具集、MCP、终端、文件、网络等 | 内置 Tool + MCP + Tool Policy + Sandbox |
| 技能 | 渐进式加载，兼容 agentskills.io | `SKILL.md` 绑定到 Agent，按需加载 |
| 记忆 | `MEMORY.md`、`USER.md`，支持多种外部记忆后端 | Agent 级 Memory，支持关键词、向量、时间融合 |
| 知识库 | 文档概览页未把企业知识库作为中心对象 | Named Knowledge Base、索引、检索、强制引用 |
| 子 Agent | 已有 `delegate_task`，最多并行 3 个 | Agent 团队协作是方向，部分能力仍在路线图 |
| 浏览器和语音 | 当前功能重点之一 | 属于路线图中的多模态和浏览器方向 |
| 回滚 | 工作目录检查点 + rollback | 更强调工具策略、沙箱和审计 |
| 调度 | 自然语言 / Cron，结果可发送到平台 | Cron、ScheduledTask、通知渠道、持久化执行记录 |
| 审计治理 | 有事件钩子、安全拦截等机制 | 从核心数据模型开始写入 LLM 与 Tool 审计表 |
| 多 Agent 管理 | 更偏多任务和子 Agent | 多 Agent 生命周期、配置、路由和管理台 |
| 企业隔离 | 文档重点不在多租户治理 | 多租户、SSO/RBAC、成本治理等列入企业路线图 |

这里不能简单说谁“功能更多”。Hermes 在浏览器、语音、图像、个人开发环境和批量轨迹生成方面更完整；oryxos 在 Agent 注册、企业配置、工具权限、知识库、审计和平台化方面更集中。

## 三、技术架构层面的区别

### Hermes：以“单个自主 Agent 的执行能力”为中心

从功能组织方式看，Hermes 的架构中心是一个能够不断行动的 Agent Runtime：

```text
用户 / CLI / 消息平台 / IDE
          ↓
      Agent Runtime
          ↓
模型推理 → 工具调用 → 观察结果 → 继续推理
          ↓
终端、文件、浏览器、MCP、记忆、子 Agent
```

它的关键架构特征是：

1. **交互入口多**：CLI、消息平台、OpenAI 兼容 API、IDE。
2. **能力插件化**：工具集、Skills、MCP、事件钩子。
3. **执行能力强**：终端、浏览器、代码执行、子 Agent。
4. **面向长任务**：检查点、回滚、Cron、记忆。
5. **模型侧路由灵活**：提供者优先级、备用模型、凭证池。

Hermes 的抽象重点是：如何让一个 Agent 在真实工作环境中完成较长、较开放的任务。

### oryxos：以“Agent 运行平台”为中心

oryxos 的架构更接近分层平台：

```text
Channel / REST API / CLI / Web Manager
                    ↓
             Agent Lifecycle
                    ↓
      ReActLoop + ContextLoader + Scheduler
                    ↓
 Provider / Memory / Knowledge / Tool / Notify
                    ↓
       SQLite Storage + Audit + Sandbox Policy
```

其技术特征包括：

1. **模块边界清晰**：`core`、`provider`、`memory`、`knowledge`、`tool`、`channel`、`web`、`storage`。
2. **核心循环自实现**：避免框架自动执行工具造成重复调用，调度权由 `ReActLoop` 和 `ToolExecutor` 掌握。
3. **Agent 配置文件化**：目录和 `AGENT.md` 是 Agent 的主要定义单元。
4. **能力契约化**：Memory、Knowledge、Provider、Tool 等通过接口解耦。
5. **治理前置**：工具策略和沙箱分别控制“能不能调用”和“调用时能碰什么资源”。
6. **审计持久化**：LLM 调用和工具调用写入数据库，不只依赖日志。
7. **运行时管理**：Provider、通知渠道、Agent 可以通过 REST 和管理台变更。
8. **当前偏单节点**：SQLite 和单进程部署简单；分布式存储、集群调度、多租户还在路线图。

所以，二者技术取向可以这样描述：

- Hermes 优先解决“一个 Agent 如何拥有更多行动能力”；
- oryxos 优先解决“多个 Agent 如何以统一方式被运行和治理”。

## 四、企业价值层面的区别

### Hermes 的企业价值

Hermes 对企业的价值主要来自个人生产力和技术自动化：

- 把工程师的终端、浏览器、代码和知识工作统一到一个 Agent；
- 通过 MCP 接入 GitHub、数据库、文件系统和内部 API；
- 用 Cron 和消息平台承载自动化任务；
- 用子 Agent 并行处理研究、开发和信息收集；
- 用批量模式生成训练或评估数据；
- 通过自托管和本地模型降低部分数据外流风险。

它更适合从“个人专家工具”或“技术团队效率工具”切入，再逐步接入组织系统。

### oryxos 的企业价值

oryxos 更直接面向组织级运行：

- **标准化**：把 Agent 定义成可复制的目录和配置；
- **可治理**：工具白名单、命令和域名限制、沙箱；
- **可审计**：可以回答“哪个 Agent 在什么时候调用了什么工具、用了哪个模型”；
- **可集成**：REST API 和通知渠道适合连接 CRM、工单、客服、运营系统；
- **可持续运行**：定时任务、长期记忆、知识库和执行记录；
- **可控成本**：Provider Registry、模型路由、调用记录为后续成本治理提供数据；
- **适合私有化**：单体部署、企业内网运行、数据留在基础设施内部。

它解决的问题更接近“如何把 Agent 变成组织的数字员工运行底座”。

### 企业价值并不只由功能数量决定

实际采用时，关键变量通常是：

- 任务是否开放式，还是流程较固定；
- 是否需要浏览器、语音、多媒体；
- 是否有严格的权限与审计要求；
- 是单个专家使用，还是多个部门共享；
- 是否需要知识库和企业数据边界；
- 是否要接入现有消息、工单、CRM、ERP；
- 是否需要横向扩展、多租户和高可用；
- 企业是否愿意维护 Agent 的工具、策略和运行环境。

因此，Hermes 和 oryxos 更像是不同层次的系统设计，而非简单的竞品替代关系。

## 五、从两者看“什么是 Agent”

可以把 Agent 拆成六个必要部分：

```text
Agent =
  目标与身份
+ 上下文
+ 推理与规划
+ 工具及执行环境
+ 记忆与状态
+ 约束、反馈和交付
```

只有模型输出文本时，它更接近“语言模型调用”。当系统具备以下闭环时，才更接近 Agent：

```text
理解目标
  ↓
决定下一步行动
  ↓
调用工具或委派任务
  ↓
观察执行结果
  ↓
更新上下文和状态
  ↓
继续行动或交付结果
```

因此：

- **Tool** 是 Agent 的手；
- **Memory / Knowledge** 是 Agent 的长期状态和外部知识；
- **ReAct Loop** 是 Agent 的行动机制；
- **Sandbox / Policy** 是 Agent 的边界；
- **Scheduler / Channel / API** 是 Agent 的工作入口；
- **Audit** 是 Agent 在企业中的可追责性；
- **Model** 只是 Agent 进行判断的一个组件。

这也是为什么“Agent OS”这个说法有一定技术含义：它不是把大模型换成操作系统，而是把 Agent 的生命周期、能力注册、执行、状态、权限、调度和审计组织成类似操作系统的运行层。

## 六、一个更中性的结论

Hermes Agent 和 oryxos 都在构建 Agent Harness，也就是模型之外的执行支架，但重心不同：

- Hermes 更接近“高能力、强交互、面向个人和技术任务的自主助手”；
- oryxos 更接近“可部署、可管理、可审计、面向企业 Agent 集群的运行平台”。

二者共同说明了一点：

> Agent 的核心竞争力不只取决于模型能力，而取决于系统能否把模型的判断稳定地转化成受约束、可观察、可恢复、可持续的行动。

对于 oryxos，真正需要继续回答的也不是“再增加多少工具”，而是：

1. Agent 如何可靠地完成跨步骤任务；
2. 多个 Agent 如何分工、通信和互相校验；
3. 企业如何定义权限、责任和审批边界；
4. 如何度量 Agent 的成功率、成本和业务结果；
5. 如何让 Agent 从一次性脚本演化为可运营的组织能力。
